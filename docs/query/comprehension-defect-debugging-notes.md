# 模式推导正确性缺陷：排查经验与结论

> 记录一个耗时十一轮的缺陷排查过程。目的不是复述结论，而是**保留做对了什么、做错了什么**，
> 供后续遇到「同一函数里存在多个独立缺陷」这类问题时复用。
>
> 结论本身（根因、修法、验收）见
> [deferred-pattern-comprehension-findings.md](deferred-pattern-comprehension-findings.md)。

## 一、缺陷与最终根因

**症状**：LDBC complex-10 的 `commonInterestScore` 错误；`size([x IN posts WHERE (x)-[:HAS_TAG]->()<-[:HAS_INTEREST]-(person)])`
在特定查询里数错元素。

**根因**：`bindExistsSubPlan`（`src/query/planner/binder/bind_match.cpp`）用**局部计数器**命名保存槽：

```cpp
uint32_t chain_counter = 0;                      // 每次调用从 0 开始
std::string saved_var = "__exists_saved_" + std::to_string(chain_counter);
```

同一条语句里编译的**两个子计划都生成 `__exists_saved_1`**；二者都注册进 `ctx_.symbols`，
于是后编译者按名字解析到前者的绑定 —— 与 `NOT <模式谓词>` 同处一个 WHERE 的**模式推导
读到别的子计划的保存值**，静默丢弃终点约束。

**修法**：后缀改用 binder 全局计数器 `nextAnonId()`，一行改动。

## 二、为什么花了十一轮：三个结构性原因

### 1. 那个函数里有多个**真实但无关**的缺陷

排查中先后确认并「修好」了至少五个独立缺陷，**每一个都不改变目标行为**：

| # | 找到的缺陷 | 是否目标成因 |
|---|---|---|
| 1 | `collectAllVariables` 不收集模式绑定的变量 | 否 |
| 2 | 注册额外关联变量时类型硬编码 `Vertex()` | 否 |
| 3 | 按 slot 反查变量名存在歧义 | 否 |
| 4 | Apply 与 SemiJoin 共用 source、列集合需求冲突 | 否 |
| 5 | **`__exists_saved_N` 命名冲突** | **是** |

**教训**：「找到一个真实缺陷」≠「找到成因」。在没有**能区分正确/错误的判据**之前，
不应把局部缺陷当成结论。

### 2. 判据不独立（最贵的错误）

我多次用**同源机制**做验证，于是「验证通过」毫无意义：

| 错误的判据 | 为何无效 |
|---|---|
| 用 `size([(…)\|1])` 当「独立路径」 | 它本身就是模式推导，与被测机制同源 |
| 用两个**约束不等价**的查询对比（一侧含 `NOT (friend)-[:KNOWS]-(person)`、另一侧不含） | 得到「0 vs 381」的假差异，据此追了数轮 |
| 用单元测试 fixture 断言，但**没先确认 fixture 能触发缺陷** | 真正的缺陷不在被测路径上 |

**教训**：判据必须**独立于被测机制**，且**先证明它能区分对错**（先让它在缺陷存在时失败）。

### 3. 在小样本上做总结

我曾据一个被污染的库、或一个被实验残留影响的数据目录下结论，得到与真实相反的方向。

## 三、做对了什么（最终成功的三个动作）

### 1. 换独立视角核对 —— 对 neo4j

在反复「猜机制→改代码→撤回」之后，改为**用 neo4j 核对期望值本身**。
这迫使我怀疑自己的断言，而不是继续给缺陷编机制。

### 2. 写最小单元测试，把触发条件固化成 fixture

这是**转折点**。之前一直在真实数据集（1528 人、14073 条 KNOWS）上观察，
变量太多；写成 7 行 fixture 后，**触发条件被压缩到一眼可读**：

```cypher
MATCH (person:UT_P {id: 1})-[:UT_KNOWS]->(m:UT_P {id: 99})-[:UT_KNOWS]->(friend:UT_F)
WHERE NOT friend=person AND NOT (friend)-[:UT_KNOWS]-(person)   -- 触发条件
OPTIONAL MATCH (friend)<-[:UT_CREATED]-(post:UT_Post)
WITH friend, collect(post) AS posts, person
RETURN size([x IN posts WHERE (x)-[:UT_HAS_TAG]->()<-[:UT_INTEREST]-(person)])
```

**命名冲突在 fixture 上立刻显形**（`__exists_saved_1` 只能有一个）。

### 3. 从**已知能复现**的一侧做删减二分，而不是从理论一侧猜

不再问「理论上哪里可能错」，而是：**保留能复现的最小集合，逐个删元素**。
一次就定位到 `NOT <模式谓词>` 是唯一必需条件，并**顺带否证了前面全部假设**
（datetime 过滤、变长路径、`pc`/`cpc` 共存、列布局……）。

## 四、可复用的检查清单

遇到「改了但行为不变」或「同一处反复出错」时：

1. **先写出一个能区分对错的判据**，并确认它在缺陷存在时**确实失败**；
2. **判据必须独立**：不要用与缺陷同源的另一条路径「验证」；
3. **从能复现的最小输入做删减二分**，而不是从理论猜机制；
4. **期望值要用外部实现核对**（此处是 neo4j），而不是自己推断；
5. 找到「一个真实缺陷」后，**先验证它是否改变目标行为**，再决定是否继续；
6. 大改动前先做**单变量隔离实验**（逐处禁用 + 跑全量测试），避免把合并效果当成单个改动的功效；
7. 性能结论必须**同二进制交错 A/B**，并确认机器状态（本机 CPU 会降到 33% 频率）；
8. **测试写完后要确认它真的能失败**——通过的测试可能什么都没覆盖。

## 五、附带发现（独立的既有缺陷）

排查中顺带确认、与本缺陷无关但值得单独处理：

* **反向关系模式不匹配**：同一份数据上 `MATCH (post:Post)-[:CREATED]->(p:P)` 有结果，
  而 `MATCH (p:P)<-[:CREATED]-(post:Post)` 返回空；
* **`bindExistsSubPlan` 的关联变量注册类型硬编码 `Vertex()`**，对 LIST 等非顶点类型不成立；
* **按 slot 反查变量名有歧义**：一个 slot 上可能坐着多个名字；
* **Apply 与 SemiJoin 对同一 `CorrelatedSource` 的列集合需求不同**，单一列集合无法同时满足。
