# 在线索引构建（后台任务 + 变更表 + 状态机）设计

> 目标：把索引创建从"**同步、单事务、阻塞式**"改造成"**后台任务 + 状态机 + 变更表追赶**"，
> 使其满足三件事：① 已有数据上建索引不阻塞写入；② 构建期间的新写入不丢（最终一致落入索引）；
> ③ 构建完成后索引一定完整（杜绝"空索引 + `PUBLIC`"这类静默漏结果）。
> 参考 PostgreSQL 的 `CREATE INDEX CONCURRENTLY`（两遍扫描 + 短暂锁）与 MySQL InnoDB 的
> online DDL（log 表 + 最后加锁重放）。

## 1. 现状与问题

| 现状 | 问题 |
|---|---|
| `CREATE INDEX` 在查询执行器里**同步**跑完：建定义 → 单事务回填 → 置 `PUBLIC` | 大标签回填耗时数十秒且**整个回填包在一个事务**里（缓存/更新链表压力大） |
| 回填期间新写入**直接写索引**（`WRITE_ONLY` 也算 live） | 回填快照与新写入交错，无一致性保证（唯一索引更甚） |
| 回填事务提交失败**不检查**（见 `loader-design.md` §12.3；已修"失败置 ERROR"） | 曾经出现"索引 0 条却 `ONLINE 100%`" ⇒ 规划器选中空索引 ⇒ **静默漏结果** |
| 进度只有 `populationPercent` | 无法区分"扫描基础数据 / 追赶变更 / 最终加锁" |

## 2. 目标与非目标

**目标**

1. 索引创建是**后台任务**：`CREATE INDEX` 立即返回，构建在后台推进，可观测进度与状态；
2. **已有数据 + 实时写入**都能正确进索引（变更表 + 追赶 + 最终加锁）；
3. **未完成（非 `PUBLIC`）的索引绝不被规划器使用**（读路径只用 `PUBLIC`）；
4. 构建过程**可中断、可诊断、失败可恢复**（失败必须显式 `ERROR`，绝不假 `PUBLIC`）；
5. 一个图内**索引构建串行**（见 §8）。

**非目标**

* 不做并行索引构建（同一图内多任务并发扫描）；不做在线 DROP（本期只要求 DROP 安全，不要求零阻塞）；
* 不引入外部任务队列/持久化调度器（复用图内的后台执行上下文）；
* 不改写索引键编码（`IndexKeyCodec`）与 KV 布局（见 `kv-encoding.md`）。

## 3. 索引状态机

**四条核心不变量（实现时逐条对照，任何改动都要过这四条）**

| # | 不变量 |
|---|---|
| **I1** | **非 `PUBLIC` 永远不可读**：`planner(index) ⇒ state == PUBLIC` |
| **I2** | **`BUILDING` 下每个已提交写入有且仅有一个维护去向**：`BUILDING ⇒ delta`、`PUBLIC ⇒ index`；**不存在**"一部分写 delta、一部分写 index" |
| **I3** | **`FINALIZING` 是唯一的分界线（finalization line）**：线前写者一律 delta 且必须在排空前结束（commit/rollback）；线后写者一律直写 index |
| **I4** | **`PUBLIC` 是"完整性证明"**：`state == PUBLIC ⇒ 基础扫描完成 ∧ delta 已逻辑清空 ∧ 校验通过 ∧ 唯一约束成立 ∧ 对规划器安全` |


| 状态 | 含义 | 读路径（规划器） | 写路径（维护） |
|---|---|---|---|
| `ABSENT` | 定义不存在 | 不可用 | 无 |
| `BUILDING` | 正在扫描基础数据 | **不可用** | 写入**变更表** |
| `BUILDING(phase=CATCHUP)` | 基础扫描完成，反复重放变更表 | **不可用** | 写入**变更表** |
| `FINALIZING` | 已加锁，重放最后一批变更并校验 | **不可用** | **被锁阻塞**（见 §7） |
| `PUBLIC` | 可用 | **可用** | 直接写索引 |
| `ERROR` | 构建失败（唯一冲突、提交失败、崩溃） | 不可用 | 无（保留定义供 `DROP`/重建） |
| `DROPPING` | 已下达删除：新查询不再选它，但**数据保留**给在飞查询 | **不可用** | 不再维护 |
| `PURGING` | 在飞使用者已归零，正在删除索引表/变更表/定义（幂等） | 不可用 | 无 |

**状态与阶段的划分依据（只有"是否改变写入去向"才配当独立状态）**：

* `BUILDING` 的 `phase ∈ {SCAN, CATCHUP}`：两者对**写路径、读路径、DDL 的行为完全相同**（都写变更表、都不可用），
  差别只在构建器自己在做什么与进度口径。因此它们是**同一状态的两个阶段**（本文其余处写 `CATCHING_UP` 的地方，
  均指 `BUILDING(phase=CATCHUP)`），不新增状态迁移。
* `FINALIZING` **必须独立成状态**：它**改变写入去向**（关闸 ⇒ 新写排队），是唯一需要**排它 latch** 的迁移。

* 与现有 `IndexState{WRITE_ONLY, PUBLIC, ERROR}` 的映射：`BUILDING`/`CATCHING_UP`/`FINALIZING`
  统一取代旧的 `WRITE_ONLY`（旧值仅作为兼容读入时的别名）；**读路径判定从"状态 ∈ {WRITE_ONLY, PUBLIC}"
  收紧为"状态 == PUBLIC"**——这是第 3 条目标的落地方式，也是本次重构最重要的语义变更。
* `populationPercent` 保留，另加 `phase`、`deltaBacklog`、`startedAt`、`error`。

## 4. 写路径规则（唯一需要热路径配合的地方）

写入实体时，对**每个受影响的索引**按状态决定动作：

1. `PUBLIC` ⇒ 直接写索引表（现状行为，不变）；
2. `BUILDING` / `CATCHING_UP` ⇒ 写**变更表**（同事务，见 §5）；
3. `FINALIZING` ⇒ **阻塞等待**（毫秒级，见 §7）；
4. `ERROR` / 不存在 ⇒ 不维护。

**判定与落盘必须原子**：状态读取 + 分支 + 写入要在**同一临界区内完成**，否则会出现
"读到 `BUILDING` → 状态翻到 `FINALIZING` → 仍写变更表"而最终批已扫完 ⇒ **该写入永久丢失**。
实现：每索引一把**读写锁**（写者持共享锁，`FINALIZING` 持排它锁），或等价的"状态 epoch 校验 + 重试"。
（倾向后者：无阻塞读、只在极少数冲突时重试。）

## 5. 变更表（delta）设计

### 5.0 表结构

| 项 | 设计 | 理由 |
|---|---|---|
| 表 | **一索引一表** `idx_delta_<index_id>`（该图 data store 内，随图回收） | 每索引独立重放/清理；`DROP` 时一并删；避免跨索引耦合 |
| 键 | **`(index_key_bytes, entity_id)`**（索引键在前，实体 id 在后） | ① 重放可**按键序**扫描 ⇒ 相同键的条目**相邻**，唯一性自查只需比相邻项；② 天然去重 |
| 值 | `{op: PUT｜DEL, payload}`（payload 为边索引的邻接值；顶点索引通常为空） | 复用索引表的键编码（`IndexKeyCodec`），重放即"原样写入/删除" |
| 去重 | **同一 `(key, entity)` 覆盖写** ⇒ 每个键-实体对最多一行 | 追赶代价与"**被改动的键数**"成正比，而非写入次数 |
| 键变更（UPDATE 换值） | **两行**：旧键 `DEL` + 新键 `PUT`（同事务） | 保证"旧条目必被清、新条目必被建" |
| 墓碑 | `DEL` **无条件记录**（即使目标条目尚未建） | 因为构建可能"稍后才扫到该行并建条目"；重放时"删不存在的条目"是 **no-op** ⇒ 幂等 |
| 事务 | 与实体写入**同一事务** | 沿用既有不变量：索引条目不得与实体数据分离提交；回滚即一并消失，提交即一并可见 |

**四条不变量**

1. **幂等**：`PUT`/`DEL` 重复应用结果相同 ⇒ 重放可安全重试（也为将来"崩溃续建"留路）；
2. **只看已提交**：构建器每轮用**新的快照事务**读变更表 ⇒ 不会看到未提交的实体/变更；
3. **同图至多一张活跃变更表**：构建在图内**串行**（§8）⇒ 任何时刻至多一个索引处于 `BUILDING`；
4. **`backlog` 可廉价获取**：以行数计（计数器或表统计），**仅作调度启发式**；
5. **`backlog ≤ 阈值` 只是"值得尝试 `FINALIZING`"的信号；正确性条件是"delta 真正为空"**——
   进入最终阶段后必须**扫描 delta 到 EOF** 才能判定清空，**永远不得**用 `counter == 0` 代替（计数器未来可能近似化，那是埋雷）；
6. **`WT_ROLLBACK` 必须重试整个事务**，不能只重试当前 cursor 操作：WT 回滚会使事务整体失效、cursor 状态被重置
   ⇒ 实现必须是 `begin → apply_batch → (conflict ? rollback + continue : commit)` 的**整事务重试循环**。（写进实现规范，不只放在测试里）


### 5.1 唯一索引在构建期间的约束语义（已定：**构建期不做唯一性强制**）

**结论**：`PUBLIC` 之前，唯一索引**不强制唯一**——不做 keyed latch、不做预留行、写路径不探测。
理由：并发写入之间**互相看不见**（未提交不可见），靠"探测"根本无法保证唯一（H5）；为它引入
per-key 锁或预留行会带来写路径串行化与事务被打回重试的代价，**不值得**。

**规则**

1. `BUILDING`（含 `phase=CATCHUP`）：唯一索引与普通索引**走同一条写路径**——写变更表，**不校验唯一性**；
   期间允许出现重复键（**语义上"唯一约束尚未生效"**，需在文档与 `SHOW INDEXES` 明确）；
2. **唯一性校验分三类，尽量移出临界区**（发现重复 ⇒ **构建失败**：置 `ERROR`，报告冲突键与冲突实体 id，
   **绝不带重复键上线**）：

   | 校验 | 时机 | 代价 |
   |---|---|---|
   | **索引内自查**（基础数据里的历史重复） | `phase=SCAN` 结束后、`CATCHUP` 期间：对已建索引做**一次全扫描、按键序比较相邻项**，尽早失败 | O(索引大小)，**不持闸门** |
   | **变更表内自查** | 每轮重放**按键序**扫描时顺手比较相邻项（同键不同实体 ⇒ 重复） | **零额外扫描** |
   | **变更表对索引自查** | 关闸后**最后一批**（已降到阈值以下）逐个 point-lookup | 有界（阈值量级），在临界区内 |

   > **为什么不能在 SCAN 阶段"与前一 key 流式比较"**：主数据扫描是**按实体 id 序**（标签全量遍历）进行的，
   > 而索引键由属性值派生 ⇒ **写入顺序不是键序**，相邻写入不等于相邻键，流式比较**无效**。
   > 能按键序廉价比较的是**索引自身**（B-tree 按键序）⇒ 因此把"历史重复"的检查放在 SCAN 之后的索引全扫描里。
3. 自 `PUBLIC` 起，唯一约束**正常生效**（写路径按索引查重，冲突拒绝写入）；
4. **装载顺序（更正后的结论）：先建索引 → 等它 `PUBLIC` → 再装载**

   | 顺序 | 适用 | 说明 |
   |---|---|---|
   | **A. 建索引 → 等 `PUBLIC` → 装载**（**唯一正确顺序**，loader 现状） | **主键/唯一索引**，以及 loader 的全部索引 | ① 空表建索引 ⇒ 扫描 0 行、变更表为空 ⇒ **立刻 `PUBLIC`，不存在"追赶"**；② 装载期写入**直写索引**，全程强唯一，零变更表开销；③ **写边时必须用主键索引解析端点**（loader 把端点主键值发给服务端做解析）——索引不是 `PUBLIC` 就**不可用**，边根本写不进去 |
   | **B. 装载 → 后台建索引** | 仅**事后补二级索引**（非唯一、非端点解析所需） | 这时才有"基础扫描 + 变更表追赶"；数据本身有重复的唯一索引 ⇒ 构建失败并报出冲突键 |

   **禁止 C：装载与构建并发**（见 H19）：变更表会持续增长、追赶饥饿，且唯一冲突要等到很晚才发现。
   **推论**：对 A 来说，本文档的变更表与追赶机制**完全用不上**（空表构建）——它们是给 B 用的。


### 5.2 变更表的清理时机

| 时机 | 动作 | 依据 |
|---|---|---|
| **构建成功（置 `PUBLIC`）之后** | 删除变更表（可**异步/延迟**） | 闸门已翻到 `PUBLIC`（写路径直写索引），此后**不会再有人写**变更表 ⇒ 删除安全 |
| **构建失败（置 `ERROR`）** | 删除变更表 | `ERROR` 状态下写路径不再维护它（不再写入）；本期不做崩溃续建 ⇒ 重试即"从零重建" |
| **构建中被取消 / 被 `DROP`** | 先取消构建（开闸）、再删变更表，然后走 `DROPPING → PURGING` | §7.2；必须先确保构建器已停止写入 |
| **启动时**：索引状态为 `BUILDING`/`FINALIZING`（崩溃残留） | 标 `ERROR` + 删除其变更表 | 本期不做续建（决策）；删除是幂等的 |
| **启动时**：孤儿变更表（无对应索引定义） | 删除 | 索引 id **永不复用**（H15），因此可安全判定"无定义 = 孤儿" |
| **`DROP INDEX` 完成（`PURGING`）** | 删除索引表 + 变更表 + 定义 | 幂等；`PENDING_PURGE` 超时兜底由后台清扫完成 |

**不需要**做的事：不需要对变更表做**压缩/合并**（`(key, entity)` 覆盖写本身就是去重；若采用 §6.1 方案①，已应用的行会被逐行删除，表只保留未应用的变更），也不需要限制写入速率——
"一直追不上"由 §7.1 的**关闸 + 排空**解决：backlog 大时构建留在 `CATCHUP` 继续重放（**闸门不开**），
只有 backlog 降到阈值以下才关闸 ⇒ **临界区只覆盖最后一批**。


### 5.3 变更表的空间成本与测量判据（WT 内部）

* **清理一律用 `WT_SESSION::drop`**：删变更表直接 drop（WT 内部移除表与页面元数据，远快于逐行删）——
  §5.2 的所有删除动作都按 drop 实现；
* **墓碑/空间成本**：方案① 在构建期间对同一张表不断 `PUT`+`DELETE` ⇒ 页面里会留下"已删除但尚未被
  reconciliation 回收"的空间，重放扫描要跳过它们。**注意措辞**：我们的表是 **B-tree**（未配置 `type=lsm`），
  机制是"删除键的可见性判断 + 页面 reconciliation"，**不是 LSM 压实** ⇒ 不能照搬 LSM 的调优结论；
* **测量判据（P2 落地后必测，先有数据再调参）**：构造"高写入速率 + 长时间构建"，测
  **重放吞吐随构建时长的衰减**与**变更表实际占用**。若重放速率衰减明显（如降到初期 50% 以下）⇒
  切方案②（值带 `seq` + 水位，构建期不删行）、改**分段变更表**（按轮次/时间分多张，旧表整体 drop），或给变更表配 `type=lsm`（见 §5.4）；
  `leaf_page_max` 等表级配置**只在有测量数据之后**再调；
* 无论选哪个方案，**先落三项指标**：`deltaBacklog`、变更表占用、每轮重放耗时——没有它们无法判断是否需要优化。


### 5.4 决策记录：变更表用 B+tree（`type=row`），不用 append-only 日志

**结论：采用 B+tree**，键 `(index_key_bytes, entity_id)`。四条决定性理由（按重要性）：

1. **重放写入目标是 B+tree 索引** ⇒ 变更表**按键序**排列，重放就是"有序写入"，避免把随机写放大成
   "索引页随机分裂"；append-only 日志（按 `seq` 序）会让重放**退化为随机写**；
2. **天然去重**：同一 `(key, entity)` 覆盖写 ⇒ 表大小 ∝ **被改动的键数**，而非写入次数；
   append-only 日志随写入次数**无界增长**（热点键改 100 次就是 100 条），重放要么重复应用、要么在内存里聚合；
3. **唯一性自查只需比相邻项**（B-tree 按键序 ⇒ 同键相邻）；append-only 必须**全量聚合/排序**才能找出冲突，
   而这会拉长关闸窗口；
4. 清理都是 **drop 表**（两者相同，不构成差异）。

**成本口径（此处纠正一处常见误判）**：B+tree 变更表的写入不是"只多一点点"——每次索引维护 =
**索引一次插入 + 变更表一次 B+tree 寻址+插入**，**量级与索引写入本身相当**（≈ 2×）。
它之所以仍可接受，是因为 ① 覆盖写让表极小、页基本常驻内存；② **工作流 A（先建索引→PUBLIC→装载）
根本没有变更表**——这条最常见的路径零开销。若测量显示变更表写入成为瓶颈，备选是给变更表配
`type=lsm`（WT 的 LSM 就是 append 友好的实现，代价是后台 merge 与主引擎抢 I/O/缓存）——
**由测量决定，不预先优化**。

**另一处措辞纠正**：重放"按键序" ≠ "顺序 I/O"。索引页是否在缓存里取决于访问模式，因此重放的写入是
"**有序的、页内局部性好的写入**"，远优于随机，但不是 LSM 式顺序刷盘；评估重放收益时不要按顺序盘算。

**被否决方案：append-only 日志 `(seq, op, key, entity)` + 水位**

| 维度 | B+tree 变更表（采用） | append-only + seq 水位（否决） |
|---|---|---|
| 写路径 | 索引插入 + 变更表 B+tree 插入（≈2×） | **单次顺序追加**（最省） |
| 表体积 | ∝ 被改动的键数（覆盖写去重） | ∝ 写入次数（无界增长） |
| 重放 | 按键序，**已去重**，直接有序刷入 | 需按轮次聚合/排序去重；或容忍重复应用 |
| 关闸窗口 | 只需扫少量已排序残余行 | 需先聚合去重，窗口更长 |
| 逐行删 vs 截断 | 方案① 逐行删（可能留墓碑） | **按水位截断**，无需逐行删 |

**何时重新考虑 append-only**（测量触发，非推测）：① 变更表写入成本成为可观测瓶颈；② 方案① 的逐行删除
导致重放吞吐随构建时长明显衰减（§5.3）。届时可选：`type=lsm` 变更表，或"append-only + 分段截断"。

**WT 的三种表类型为何不选另两种**：`type=column` 只能按追加序存、**无法按键去重**（不满足 1/2/3 条）；
`type=lsm`（append 友好）作为**备选**保留，默认不用——其后台 merge 会与主引擎争 I/O 与 cache。


## 6. 构建流程（四阶段）

```
① BUILDING     扫描基础数据（分批、可提交的分段事务，不再是单一大事务）
                 └ 每批：写索引条目；同时把该批的 (key,entity) 记入"已扫水位"（可选，用于恢复）
② CATCHING_UP  反复重放变更表，直到 backlog 降到阈值以下（如 < 1% 或 < 1000 条）
                 └ 每轮重放后再取一次 backlog；这是"追赶循环"，不阻塞写入
③ FINALIZING   加排它锁 ⇒ 重放**最后一批**变更 ⇒ 校验（唯一性、条目数非 0）⇒ 置 PUBLIC
                 └ 临界区只做"重放最后一批 + 改状态"，必须短
④ PUBLIC       释放锁；删变更表（可延迟/异步）
```

**硬性护栏（吸取 §12.3 的教训）**：

* 只有 ③ 成功通过校验才允许置 `PUBLIC`；任何一步失败 ⇒ `ERROR` + 明确错误信息；
* ③ 的校验至少包含：**变更表已空**、**唯一索引无冲突**、**目标集合非空时索引条目非 0**
  （最后一条直接拦住"空索引上线"）；
* 提交失败按 §12.3 已修的方式处理（置 `ERROR`，不置 `PUBLIC`）。

### 6.1 顺序：先扫主数据 → **反复**扫变更表 → 关闸排空最后一批

**是"先主数据、后变更表"，但变更表要扫多轮**：

```
BUILDING(phase=SCAN)     扫主数据（脚本见 §6 ①②）——期间写入进变更表
BUILDING(phase=CATCHUP)  反复重放变更表，直到 backlog ≤ 阈值（每轮：新快照 → 按键序重放 → 记录进度）
FINALIZING               关闸（新写排队）+ 等在飞写事务提交 ⇒ 重放**最后一批** ⇒ 三道校验 ⇒ PUBLIC
```

**为什么必须多轮**：单轮"扫完变更表"期间**又会产生新变更** ⇒ 永远追不上（§7.1）。多轮 + 最后关闸，
把"无限追赶"变成"有界的一小批"。

**关键不变量（为什么两段之间不需要水位）**：主数据扫描在**快照事务**里做 ⇒

* 快照**之前**提交的数据：由主数据扫描覆盖（扫描按标签全量遍历，与键值无关）；
* 快照**之后**提交的数据：一定在变更表里（`BUILDING` 状态下写路径必然写变更表）；

两者**互补且无重叠**，边界精确 ⇒ 不需要"已扫水位"就能保证不漏。**注意前提**：主数据扫描可以
**分块提交**（控制事务大小），每块各自的快照即可——即使某行"块 A 读到旧值、块 B 之前又被改"，
变更表里都有对应的 `DEL`/`PUT`，而重放是**幂等**的（§5.0 四条不变量）⇒ 结果仍正确。

**重放时是否顺手删掉已应用的行（二选一）**

| 方案 | 做法 | 代价 |
|---|---|---|
| **① 应用后按键序删除**（推荐） | 重放某行后在同一事务里删掉它；`backlog` = 表行数（廉价）；并发写入同一 `(key,entity)` 时由 WT 写写冲突让**构建器**（后写者）回滚并重试本轮——**用户事务不受影响** | 构建器偶发重试；需保证"读到即删"在同一事务内 |
| ② 只应用不删（值里带 `seq`，维护水位） | 每轮只应用 `seq > 水位` 的行，表在结束时整体删 | 每轮需**全表扫描**过滤（表随构建时长增长），或需要按 `seq` 的辅助索引 |

方案 ① 让变更表**始终只装着"还没应用的变更"**，因此长时间构建也不会把它撑大；方案 ② 完全不干扰写者，
但表会随构建时长增长。**默认取 ①**（并在实现里保证构建器对 WT 冲突重试本轮）。

**空表（工作流 A：先建索引→PUBLIC→再装载）**：两段都**不需要**——主数据 0 行、变更表为空 ⇒ 直接
`FINALIZING`（校验退化）→ `PUBLIC`。

**形式化覆盖不变量（比"主数据 + delta"更准确的表述）**：

```
Index(PUBLIC)  ==  BaseScanObservedState  ⊕  CommittedDeltaAfterRelevantSnapshot
```

成立条件（实现时必须同时满足）：① `BUILDING` 状态下**每个成功提交**的写事务都产生 delta 行；
② 任何在**某个基础扫描事务的快照之后**提交的修改都在 delta 中；③ delta 的最终状态足以**覆盖该实体在索引中的旧状态**
（故 UPDATE 换键必须写"旧键 `DEL` + 新键 `PUT`"两行）；④ 重放幂等。**仅"主数据 + delta"这句话不足以指导实现。**

**事务边界硬约束**：`BUILDING` 每批一个独立事务；`CATCHUP` 每轮重放一个独立事务；`FINALIZING` 只允许**小批**事务。
**禁止**"一个事务里扫完整个标签（几十秒）再提交"——长事务会持有 snapshot、压住 cache/eviction。

## 7. 最终锁与阻塞窗口

* 锁粒度：**per-index**（不锁图、不锁表），只影响维护该索引的写路径；
* 阻塞窗口 = 重放最后一批变更的时间。为把它压到毫秒级：② 的追赶循环必须把 backlog 压到很小；
  否则（backlog 仍大）应继续留在 `CATCHING_UP`，**不得**进入 `FINALIZING`（可加"连续 N 轮 backlog 不下降 ⇒ 降级重试"策略）；
* 超时：`FINALIZING` 持锁超过阈值 ⇒ 记录告警并放弃本次 `FINALIZING`（回到 `CATCHING_UP`），避免长尾阻塞写；
* 死锁规避：锁只被"写路径维护该索引"与"构建器最终阶段"获取，二者不互相等待其它资源（写路径里不得再取其它索引的锁）。

### 7.1 进入 `FINALIZING` 前必须"关闸 + 排空在飞写事务"

**问题**（已确认）：持续写入下，追赶循环可能**永远追不上**——每轮重放期间又产生新变更，
`FINALIZING` 反复失败、构建饿死。这不是概率问题：写负载是**外生**的，靠"再追一轮"无法收敛。

**做法**（两段式，共同构成 `FINALIZING` 的临界区）：

1. **关闸（gate closed）**：该索引的写路径由"写变更表"改为"**在闸门处等待**"（带超时）；
   **已在飞的写事务继续跑完**；
2. **排空**：等待在飞写事务计数归零 ⇒ 变更表内容**有界且不再增长** ⇒ 重放一次即可清空，
   随后做三道校验并置 `PUBLIC`；
3. **开闸**：状态已切到 `PUBLIC`，被唤醒的排队者直接写索引（不再写变更表）。

**要点**

* **必须关闸**：不关闸只能追赶，而在持续写负载下这是**设计上的不收敛**（livelock），不是调参能解决的；
* **闸门必须短**：临界区只做"排空 + 重放 + 校验 + 改状态"，典型毫秒级；超时 ⇒ 开闸、退回 `CATCHUP` 并告警，
  绝不允许无限期阻塞业务写。**超时不是系统语义，而是可配置默认值**（`finalizing_timeout_ms = 1000`）：
  最终阶段耗时取决于 delta 批量、WT cache 压力、CPU、键分布、checkpoint 与存储介质 ⇒ 必须**可调**并
  记录 `finalizing_duration`、`finalizing_timeout_count`、`finalizing_backlog` 三项指标；
* **排队而非拒绝**：新写事务在闸门处等待（有超时）；闸门持有者超时开闸后，排队者正常继续
  （**构建让路给业务写**），构建退回追赶下轮再试；
* **进入 `FINALIZING` 的两个条件（缺一不可）**：① `backlog ≤ 阈值`；② **最老在飞写事务年龄 ≤ 阈值**
  （如 200ms）。第 ② 条专治"**超长写事务 ⇒ 关闸 → 排空超时 → 开闸**"的**抖动循环**（既抖业务延迟、构建又永远切不过去）：
  只要存在长事务，就**留在 `CATCHUP`** 继续重放、**不开闸**。同时记录 `gateAttempts`/`gateTimeouts` 以观测抖动；
* 影响面仅限**维护该索引**的写路径（per-index gate）：不影响其它索引、其它标签、读路径；
* 与 §7 的锁是同一件事的两个侧面：闸门管"新写入的去向"，排空管"在飞写入的收敛"。

### 7.2 `DROP INDEX` 的两阶段：先"不可选"，再延迟清理

**问题**（已确认）：若有查询正在使用该索引（计划已选它、正在扫描），**不能直接删索引数据**——
在飞查询必须能跑完，否则读到半删状态。

**做法**（两阶段）

| 阶段 | 状态 | 规划器 | 写路径 | 索引数据 |
|---|---|---|---|---|
| 1 | `DROPPING` | **不再选中它**（读路径只认 `PUBLIC`） | **继续维护**（见下，关键） | **保留** |
| 2 | `PURGING` | — | — | 删除索引表 + 变更表 + 定义（幂等） |

* **为什么 `DROPPING` 期间还要继续维护**：pin 只保护"查询能跑完"，但跑完 ≠ 结果正确——
  若在 `DROPPING` 起就停止维护，一个**在飞的长查询**在后续扫描中会读到"缺了最新写入"的索引 ⇒ **结果错**。
  因此维护要持续到**使用者归零**：`DROPPING` 只做"对**新计划**不可选"，`PURGING` 才停止维护并删表；
* **pin 的获取必须与"计划发布"原子**（否则 DROP 可插在"选好索引"与"真正拿 cursor"之间造成悬空）：

  ```cpp
  IndexHandle h = acquireForExecution(index_id);   // pin() → 复查 state==PUBLIC 且数据尚在 → 失败则重新计划
  ```

  规划器**不得**只返回裸 `index_id`；`IndexHandle` 是 RAII，负责 unpin（含取消/异常路径）。
* **在飞使用者保护**：查询在计划期"选中某索引"时对该索引 **pin**（引用计数 +1，或记录使用 epoch），
  查询结束（正常/取消/异常）时 **unpin**（RAII 保证）；`DROP` 等计数归零才进入 `PURGING`；
* **超时兜底**：等待超过阈值（如 5s，或长查询上限）⇒ 转入 `PENDING_PURGE`，由后台清扫任务在
  计数归零后清理——**绝不强行删除**；
* **与构建的关系**（已定）：构建中的索引被 `DROP` ⇒ **取消构建**（若闸门关着先开闸）→ 清理变更表 →
  按上述两阶段删除；
* **与唯一约束的关系**：自 `DROPPING` 起，该唯一约束**对新写入不再生效**（写路径已不维护它）——
  符合"用户已下达删除"的语义，需在文档与 `SHOW INDEXES` 上说明；
* **崩溃恢复**：`DROPPING`/`PENDING_PURGE` 在启动时**继续清理**（删除是幂等的，无需回滚）。

### 7.3 `PUBLIC` 可见性不变量与事务边界

**I4 的可执行版本**：

```
state == PUBLIC  ⟹  基础扫描已完成 ∧ delta 已逻辑清空 ∧ 唯一性校验通过 ∧ 条目数护栏通过 ∧ 数据已提交
```

**顺序（不可颠倒）**：先提交"最后一批 delta 的应用 + delta 清理"，**再**翻转状态为 `PUBLIC`。

**一个必须写清的实现约束**：索引**状态**存在 meta store，索引**数据/变更表**在 data store —— **跨库无法一个事务**。
因此不能做成 ChatGPT 建议的"apply + verify + state=PUBLIC 同一个 `T_final`"。正确做法是：

1. `T_final`（data store）：应用最后一批 delta + 删除已应用行 + 校验 ⇒ **commit**；
2. **之后**单独写 meta：`state = PUBLIC`（一次原子状态写）。

崩溃落在 1 与 2 之间 ⇒ 重启后状态仍非 `PUBLIC` ⇒ 按 §9 标 `ERROR`（**安全侧**：宁可重建，不可错用）。
**反序（先 PUBLIC 再提交数据）是禁止的**——那会在崩溃后留下"`PUBLIC` 但数据不全"的索引，即历史事故的形态。



**是：一个图内索引构建必须串行**，即使多个 `CREATE INDEX` 同时到达：

* 图内维护**一个构建队列 + 一个构建工作协程/线程**（复用既有的 IO/CPU 执行上下文与定时循环，参照 checkpoint 线程的模式）；
* 理由：① 变更表追赶需要"稳定的追赶对象"，多任务并发会让彼此的 backlog 抖动、`FINALIZING` 反复失败；
  ② 每个构建都要全量扫描基础数据，并发会把 IO/缓存打满，**总完成时间更差**；③ 进度/错误语义清晰；
* 不同**图**之间可并行（互不共享 data store）；
* 队列语义：FIFO；同一索引重复 `CREATE` ⇒ 幂等（已存在且非 `ERROR` 时直接返回当前状态）；
  `DROP INDEX` 与构建互斥（同队列：先完成后置的语义）；
* 用户可见性：`CREATE INDEX` 返回 `{index, state: BUILDING}`；如需同步语义，提供显式等待
  （轮询 `SHOW INDEXES` 或 `WAIT` 选项），**但默认异步**。

## 9. 崩溃恢复

* 启动时扫描状态：`BUILDING`/`CATCHING_UP`/`FINALIZING` 的索引**一律不置 `PUBLIC`**；
* **本期不做崩溃续建（已定）**，只做策略 A；后续再评估策略 B：
* 两种策略：
  * **A（安全、简单）**：标记为 `ERROR` 并保留定义 ⇒ 用户 `DROP` 后重建。理由：恢复需要"已扫水位"这类
    额外元数据，且错误恢复路径本身最容易引入静默不一致；
  * **B（体验更好）**：保留 `BUILDING` 状态并从水位续扫。作为后续增强，需先落地水位记录的持久化与校验。
* 变更表在 `ERROR`/`DROP` 时清理；孤儿变更表（无对应索引定义）在启动时回收。

## 10. 可观测与运维

* `SHOW INDEXES` 增加列：`state`、`phase`、`populationPercent`、`deltaBacklog`、`startedAt`、`error`；
* 服务端日志：状态迁移各打一行（含索引名、图、耗时、backlog、阶段原因）；
* 失败语义：唯一冲突 ⇒ `ERROR` + 冲突样例（key、两个 entity id）；提交失败 ⇒ `ERROR` + WT 错误码；
* 取消：提供取消构建的入口（置 `ERROR` 并清理变更表），取消必须能在阶段边界生效。

## 11. 兼容性与影响面

| 表面 | 影响 |
|---|---|
| Cypher/Thrift `CREATE INDEX` | 由**同步**变**异步**（返回状态而非"Index created"）⇒ 兼容性变更，需在文档与 `SHOW INDEXES` 上明确；建议保留同步等待开关 |
| `IndexState` 枚举 | `WRITE_ONLY` 语义收窄为"构建中"（`BUILDING` 系）；读路径判定收紧为 `== PUBLIC` |
| 规划器 | **只使用 `PUBLIC` 索引**（原先 `WRITE_ONLY` 也可能被用）⇒ 修复一类静默错误 |
| 载入路径（loader） | 不受影响：loader 建索引时走同一状态机（可支持"边载边建"） |
| KV 布局 | 新增 `idx_delta_<index_id>` 表；索引表布局不变 |

## 12. 测试策略（先定判据，再动手）

1. **状态机单测**：合法/非法迁移、`ERROR` 不可用、`PUBLIC` 前必须通过校验；
2. **并发写入正确性**（核心）：构建期间持续写入（含更新/删除）⇒ 置 `PUBLIC` 后
   "索引查询结果 == 全表扫 + 过滤结果"（**逐行比对**，不是只比条数）；
3. **唯一索引**：构建期间的冲突写入 ⇒ 要么构建 `ERROR` 且索引不可用，要么写入被拒；
   **不允许**出现"索引 `PUBLIC` 但含重复键"；
4. **最终锁窗口**：构造大 backlog ⇒ 断言 `FINALIZING` 不早于 backlog 达标；断言持锁时长上界；
5. **崩溃恢复**：构建中 kill -9 ⇒ 重启后该索引**不可能是 `PUBLIC`**，且规划器不使用它；
6. **规划器**：非 `PUBLIC` 索引不被选中（含 `WRITE_ONLY` 兼容别名）；
7. **空索引护栏**：目标集合非空而条目为 0 ⇒ 构建失败（回归 §12.3）；
8. **串行化**：并发提交 N 个 `CREATE INDEX` ⇒ 断言实际构建串行（日志/队列可观测），且最终全部 `PUBLIC`；
9. **端到端**：sf0.1 上"载入 → 后台建 `Message.id` 索引 → 构建期间持续写入 → `PUBLIC` 后与 neo4j 对照"
   （用 `scripts/verify_ldbc_results.py` 的判据）；
10. **关闸与排空**：持续写入压力下断言构建仍能进入并完成 `FINALIZING`（不像纯追赶那样饿死）；
    断言闸门时长有上界、超时后退回 `CATCHING_UP` 且业务写不被无限阻塞；
11. **DROP 的两阶段**：构造"长查询正在用该索引"⇒ `DROP` 必须等其结束（或转 `PENDING_PURGE` 后台清理），
    查询结果正确、无崩溃；`DROPPING` 起新查询不再选中它；
12. **唯一索引冲突**（按 §5.1 现行语义）：构建期**不做**唯一性强制 ⇒ 重复键允许进入变更表；
    `FINALIZING`/索引自查发现重复 ⇒ **构建失败**置 `ERROR`（报告冲突键），索引不进 `PUBLIC`；
    `PUBLIC` 之后冲突写入**被拒**；
13. **`WT_ROLLBACK` 下的变更表一致性**（破坏性）：高并发写同一批实体/边，强制触发 WT 写写冲突 ⇒
    断言变更表**不残留**未提交/已回滚的行，且重试后的结果与"无冲突"时**逐行一致**；
14. **WT cache 压力**（破坏性）：`cache_size` 压到极小 + 一边全量构建一边高并发写 ⇒ 断言**分块提交**生效、
    构建不因持有大量未提交页而拖垮 eviction（观测 WT cache full / eviction 指标）；
16. **状态切换竞态（最高优先级，linearization test）**：在 `enter()` 前后插入可控暂停点，穷举排列
    ——`W 读 gate` / `B CAS CLOSED` / `W ++inflight` / `W 复查` / `W 写 delta` / `W commit` / `B 排空`，
    断言最终 `PUBLIC` 后"索引结果 == 全表扫 + 过滤"**逐行一致**（这是整个设计的核心正确性测试）；
17. **跨键 UPDATE 疯狂交错**：`A→B`、`B→C`、`C→A`、`A→D`、`D→A` 并发（每行 delta 是"旧键 DEL + 新键 PUT"）
    ⇒ 断言**实体最终状态 == 索引最终状态**（而不是断言"delta 行数正确"）；
15. **装载期索引可见性**：装载期间**所有**索引必须已 `PUBLIC` ⇒ 断言边写入经主键索引解析 src/dst 成功。
    **注意**：不存在"边写入与某二级索引 `BUILDING` 并发"的测试场景——那是被 H19 禁止的组合（装载与构建不并发）。

## 15. 并发分析（状态 × 操作）

### 15.1 参与方与两条保护机制

| 参与方 | 与索引的关系 |
|---|---|
| 写路径（INSERT / UPDATE / DELETE 实体） | 按状态**分流**：直写索引、写变更表、排队等待或跳过（§4） |
| 读路径（查询） | 计划期**只选 `PUBLIC`**；选中即 **pin**（引用计数/epoch），结束（含取消/异常）**unpin**（RAII） |
| 构建任务（后台，图内串行） | 扫描基础数据 → 追赶变更表 → 关闸排空 → 校验 → 置 `PUBLIC` |
| 删除任务（`DROP`，走同一队列） | `DROPPING`（对新计划不可选，**仍维护**）→ 使用者归零 → `PURGING`（停维护 + 删表） |
| 后台清扫（`PENDING_PURGE`） | 使用者归零后删除（**绝不强行删**） |
| checkpoint 线程 / 图关闭 | 与索引无锁耦合；图关闭必须**取消并等待**构建/删除任务退出后再关 store |
| 批量装载（loader） | 一种"写路径"；其 PK 索引在装载前建好（`PUBLIC`，直写） |

**两条保护机制**（其余规则都由它们派生）：

1. **per-index build gate + 在飞写者计数**（**不是**跨事务持有的读写锁）：真正要保证的是一条
   **happens-before 边界**——"`FINALIZING` 必须等所有已经决定写 delta 的事务结束"。用**准入 + 计数**表达：

   ```
   写者 enter():                          构建器/删除器 close():
     if gate == CLOSED: 等待/重试            CAS OPEN -> CLOSED        // 关闸：不再接纳新写者
     inflight.fetch_add(1)                   while inflight != 0: wait // 等已准入的写者全部 commit/rollback
     if gate == CLOSED:  // 再检查（关键）    ... 重放/校验/切状态 ...
        inflight.fetch_sub(1); 重试
     // 至此本事务已属于"finalizer 必须等待"的集合

   写者 exit(): inflight.fetch_sub(1)       // RAII，覆盖 commit / rollback / WT_ROLLBACK / 异常
   ```

   * **为什么不用 `shared_mutex` 跨整个用户事务**：那等于把"用户事务生命周期"与"索引锁生命周期"绑定，
     而用户事务在生命周期内可能等待**其它**资源（WT 冲突、模式 DDL、业务资源）⇒ 与"持 latch 期间不得等待其它资源"
     自相矛盾，会引入 **index latch ↔ 非索引资源**的环路死锁（§15.4 的 id 排序只能防 latch↔latch）。
     gate 只是一个**轻量生命周期屏障**，与 WT 的乐观并发模型一致（读不阻塞写、写不阻塞写、冲突由 `WT_ROLLBACK` 暴露）。
   * **准入必须两阶段**（先 `++` 再复查 gate）：否则会出现"读到 `BUILDING` → 关闸 → 计数为 0 → finalize 完成 → 才写 delta"，
     正是 H1。准确表述是：**写入准入与关闸必须线性化**（不是"读状态+写"的原子性）。
   * **重试语义**：`WT_ROLLBACK` 后在同一事务内重试**保留**已占用的准入名额（构建器仍会等它），
     事务结束后若还需再写，必须**重新准入**（此时可能已关闸 ⇒ 等待）。
   * **凡改变写入去向的迁移**（`BUILDING→FINALIZING`、`PUBLIC→DROPPING`、`DROPPING→PURGING`）都必须走**关闸**这条路径。
2. **per-index pin**：读者在计划期 pin、结束 unpin；`DROPPING→PURGING` 需要 pin 归零。

**加锁方式（避免"走一步取一把锁"）**：写路径**先收集**本次写入影响到的索引集合（索引维护本来就要先算出
条目），按 **index id 排序后一次性获取**全部共享 latch，再进入实际写入；**严禁**在执行代码深处逐个获取
（那正是死锁与漏锁的温床）。latch 由 **RAII** 持有，覆盖 **commit / rollback / `WT_ROLLBACK`（写写冲突被打回）
/ 异常**全部退出路径；构建器的排它 latch 同样 RAII，超时与取消路径也必须释放。

### 15.2 状态 × 操作矩阵

| 状态 \ 操作 | 增/删/改（写） | 查询（读） | `CREATE INDEX`（同名/它名） | `DROP INDEX` | 重启后 |
|---|---|---|---|---|---|
| `BUILDING` | 写**变更表**（同事务）；唯一索引：**同样只写变更表，不做唯一性检查**（§5.1） | **不使用**该索引（走全表扫/其它索引），结果正确 | 同名：幂等返回当前状态；它名：**入队**（图内串行） | 取消构建（先开闸）→ 清变更表 → 转 `DROPPING` | **不置 `PUBLIC`**，标 `ERROR` 保留定义 |
| `CATCHING_UP` | 同上 | 同上 | 同上 | 同上 | 同上 |
| `FINALIZING`（已关闸） | 在闸门**排队等待**（带超时）；超时则开闸、构建退回 `CATCHING_UP` | 同上 | 入队 | 取消（先开闸）→ 删除流程 | 同 `BUILDING` |
| `PUBLIC` | **直写索引**（含唯一性检查，冲突拒绝写入） | **可用**（pin） | 同名：已存在 ⇒ 幂等返回；它名：入队 | 转 `DROPPING`（**仍维护**），等 pin 归零 → `PURGING` | 保持 `PUBLIC`（已持久化） |
| `ERROR` | 跳过（不维护） | 不使用 | 同名：需先 `DROP` 再建（或定义复用 + 重建）；它名：入队 | `DROPPING`→`PURGING`（清残表） | 保持 `ERROR`（可由用户重建） |
| `DROPPING` | **仍维护**（直写索引/变更表按原状态？见 §15.3 H14） | **新计划不可选**；在飞查询（已 pin）继续用且**结果正确** | 同名：拒绝（先删后建）或入队等待删除完成；它名：入队 | 幂等（第二个 `DROP` 返回"删除中"） | 继续删除流程（幂等） |
| `PURGING` / `PENDING_PURGE` | 跳过 | 不可用（已无使用者） | 同名：**等清扫完成**（索引 id 不复用，见 H15） | 幂等 | 继续清扫（幂等） |

### 15.3 危险清单（症状 → 机制 → 规则）

**写路径相关**

* **H1 跨越状态迁移的写入丢失**：写者读到 `BUILDING` 决定写变更表，随后状态翻到 `FINALIZING` 且最后一批已重放 ⇒ 该写入**永久丢失**。
  → 规则：共享/排它 latch（§15.1-1）；`FINALIZING` 的排它 latch 必须等在飞写者提交。
* **H2 只等"写调用"不够，要等"在飞写事务"**：写者已写变更表但**未提交**，排空只统计"当前在写路径里的调用" ⇒ 其提交落在排空之后 ⇒ 丢失。
  → 规则：共享 latch 覆盖**整个事务**（首次触及该索引 → 提交），排空等的是**事务**不是调用。
* **H3 删除/更新与基础扫描交错**：扫描期间行被删/改 ⇒ 可能留下"实体已不存在"的索引条目。
  → 规则：基础扫描在**快照事务**里做（看不到快照后的写）；快照后的写进变更表；`DELETE` 类变更在重放时对不存在的条目**幂等无操作**。
* **H4 陈旧 `DELETE` 覆盖新写入**：变更表里的 `DELETE`（旧）在重放时删掉了**之后**直写进索引的新条目。
  → 规则：写入去向的改变必须与排空互斥（H1/H2 同一把 latch）⇒ 直写只可能发生在排空**之后**。
* **H5 并发唯一写入互相看不见**（**已按决策消解**）：两个事务同时对同一唯一键 INSERT，各自探测都看不到对方（未提交不可见）⇒ 双双通过。**不加锁就不可能解决**。
  → 规则：**构建期不强制唯一**（§5.1）：写路径不探测、不加锁，重复键允许进入变更表；唯一性在 `FINALIZING`
  校验、`PUBLIC` 后强制。代价是"事后才发现重复 ⇒ 构建失败"，用工作流 A（先建索引再装载）规避。
* **H6 唯一性校验必须理解变更表的语义**（`FINALIZING`/增量校验里）：同一键在变更表里有 `DELETE`（键被释放）
  时应视为**不冲突**。
  → 规则：校验按**有效状态**判定 = 索引命中且未被变更表删除，或变更表有 `INSERT`；同一实体多次变更按最终 `op` 计。
* **H7 多索引写入的锁序**：一次实体写入可能触及多个索引（状态各异）。
  → 规则：按 **index id 升序**取 latch；**同一时刻只持一个排它 latch**；持 latch 期间不得等待其它非索引资源（如全局锁）。
* **H8 写者持有 latch 过长**：长事务会拖长 `FINALIZING` 的排空等待。
  → 规则：闸门/排空有超时（默认 1s）⇒ 超时开闸、构建退回 `CATCHING_UP`（让路给业务）、告警；**不阻塞业务**。

**读路径相关**

* **H9 读到"未完成"的索引**：非 `PUBLIC` 索引被规划器选中 ⇒ 静默漏结果（历史事故）。
  → 规则：读路径判定**收紧为 `== PUBLIC`**；`PUBLIC` 的翻转是**单次原子写**（release）且发生在校验通过之后。
* **H10 `DROP` 使在飞查询结果变错**：`DROPPING` 起停止维护 ⇒ 长查询后续扫描读到"缺最新写入"的索引。
  → 规则：`DROPPING` **继续维护**，到 pin 归零（`PURGING`）才停（§7.2，本次修正）。
* **H11 pin 泄漏导致永不删除**：查询异常/取消路径没 unpin。
  → 规则：pin 用 RAII 持有；`DROPPING→PURGING` 有超时兜底 ⇒ `PENDING_PURGE` + 后台清扫（**不强行删**）。

**DDL 之间 / 与生命周期**

* **H12 并发 `CREATE INDEX`**：多个构建互相抖动 backlog、争抢 IO。
  → 规则：图内**串行队列**（§8）；同名幂等；不同图可并行。
* **H13 构建中 `DROP`**：构建器往已被删的表里写。
  → 规则：`DROP` 与构建同队列互斥；构建器每批检查**取消令牌**，并先开闸再退出。
* **H14 `DROPPING` 期间写路径的去向**：若 `DROPPING` 时状态已从原状态（如 `BUILDING`）改写，写路径可能失去"变更表"这一去处。
  → 规则：`DROPPING` 记录**回退状态**（`dropsFrom`）：原为 `BUILDING/CATCHING_UP` ⇒ 继续写变更表（构建已被取消，仅作暂存，删除时一并清理）；原为 `PUBLIC` ⇒ 继续直写索引。**不得**因为删除而让写入无处可去。
* **H15 索引 id 复用 vs 待清扫**：`PENDING_PURGE` 期间若新索引复用了同一 id，清扫会删掉**新索引的表**。
  → 规则：索引 id **单调递增、永不复用**（与"store id 永不复用"同一教训）；清扫按 (id, generation) 校验。
* **H16 模式 DDL 与构建并发**：`createLabel`/`dropLabel` 改变属性 id，而构建正在按 (label, prop) 解析表。
  → 规则：**模式 DDL 与索引构建在同一队列上互斥**（图内串行），或构建期对 (label, prop) 解析结果做版本校验。
* **H17 图关闭与构建并发**：`dropGraph` 关 store 时构建仍在跑 ⇒ 用已关闭的连接（历史上有同类崩溃）。
  → 规则：图关闭先**取消**构建并**等待**其退出，再关 store；构建器在阶段边界检查取消。

**其它**

* **H18 checkpoint 与闸门**：checkpoint 可能拉长关闸窗口。
  → 规则：闸门有超时上界；checkpoint 不取索引 latch，但**关闸窗口内不做长等待**（超时即退回）。
* **H19 批量装载与构建**（**已定，结论已更正**）：**装载必须发生在索引 `PUBLIC` 之后**——不只是为了避免追赶，
  更因为**写边要先用主键索引解析端点**，索引不可用则边写不进去。
  → 规则：**唯一正确顺序 = 建索引 → 等 `PUBLIC` → 装载**（空表构建，无追赶）；装载与构建**不得并发**；
  需要"事后补二级索引"时才走"装载 → 后台建索引"（此时才有变更表与追赶）。
* **H20 唯一约束在 `DROPPING` 起失效**：用户已下达删除，约束不再对新写入生效；但**在飞**写入仍按旧规则。
  → 规则：语义在文档与 `SHOW INDEXES` 中明确；`DROPPING` 的迁移同样要过排它 latch（H1）。

### 15.4 锁序与死锁规避

1. 只按 **index id 升序**取 latch；
2. **一次只持一个排它 latch**；
3. 持 latch 期间**不做**跨资源等待（不取全局锁、不等待用户事务）；
4. 闸门/排空/清扫全部**有超时**，超时一律"回退 + 告警"，不制造无限等待；
5. 构建与删除走**同一图内队列**，从源头消除大部分交叉（H12/H13/H16）。

### 15.5 对应的测试（补齐 §12）

* H1/H2/H4：构建期间持续写入（含更新键值、删除实体）⇒ `PUBLIC` 后"索引查询结果 == 全表扫+过滤"**逐行比对**；
* H5/H6（按 §5.1 现行语义，分两阶段断言）：
  **构建期**并发对同一唯一键 INSERT ⇒ 两个事务**都成功**、变更表里可有两条 ⇒ 构建最终 **`ERROR`**、绝不 `PUBLIC`；
  **`PUBLIC` 后**并发对同一唯一键 INSERT ⇒ **至多一个成功**；键被删除后再 INSERT ⇒ 成功；
* H9/H10：非 `PUBLIC` 索引不被选中；`DROP` 与长查询并发 ⇒ 查询结果**正确**且无崩溃；
* H11：查询被取消/超时 ⇒ pin 归零（不泄漏），索引最终能被删除；
* H14/H15：构建中 `DROP` ⇒ 后续写入不报错、清扫不影响新建索引（id 不复用）；
* H17：构建中 `dropGraph` ⇒ 无 use-after-close 崩溃，任务退出；
* H19：装载与构建并发的策略生效（拒绝或排队）。

## 14. 已定决策与剩余待定问题

**已定（本次拍板）**

| 决策 | 结论 |
|---|---|
| `CREATE INDEX` 语义 | **异步**（返回 `{index, state: BUILDING}`）；可选显式等待 |
| 唯一索引在构建期间的语义 | **构建期不强制唯一**（`PUBLIC` 前允许重复落入变更表；`PUBLIC` 起正常强制）；`FINALIZING` 必须校验，发现重复 ⇒ **构建失败**，不带重复键上线。原"冲突写入被拒绝"的方案**已废弃**（并发写入互相不可见，不加锁无法保证，见 H5） |
| 装载与构建 | **先建索引 → 等 `PUBLIC` → 再装载**（写边需用主键索引解析端点；空表构建无追赶）；装载与构建不并发；"装载后再建"仅用于事后补二级索引 |
| 崩溃续建 | **本期不做**（构建中的索引重启后一律不置 `PUBLIC`，标 `ERROR` 保留定义） |
| 构建期间 `DROP INDEX` | **取消构建 + 清理**（先开闸，再清变更表，再按两阶段删除） |
| 进入 `FINALIZING` 前 | **必须关闸并排空在飞写事务**（见 §7.1）：不关闸在持续写下不收敛 |
| `DROP` 与在飞查询 | **两阶段**（见 §7.2）：先不可选、保数据，使用者归零后清理；超时转 `PENDING_PURGE` 后台清扫 |

**剩余待定（已按审阅建议拍板）**

| 项 | 结论 | 理由 |
|---|---|---|
| 闸门（`FINALIZING`）超时 | **可配置默认 1000 ms**（非系统语义） | 超时即开闸让路给业务写、退回 `CATCHUP`；须监控 `finalizing_duration`/`timeout_count`/`backlog` |
| `PENDING_PURGE` 等待 | **30 s**（原拟 5s 过短） | 图遍历类长查询常达秒级，5s 会频繁误判并刷告警 |
| 唯一索引严格模式 | **一期不做** | 工作流 A（先建索引→PUBLIC→再装载）已覆盖主场景；事后补建走 `FINALIZING` 校验失败即可 |
| `PENDING_PURGE` 触发 | **unpin RAII 回调（零延迟）+ 10s 定时兜底** | 回调保证及时；定时任务兜住"计数泄漏"这类异常 |
| 显式等待接口 | **优先 `CALL db.awaitIndex(name, timeout_ms)`**；`WAIT` 关键字作为后续可选 | 存储过程不改语法（兼容性风险低），对 CI/运维脚本也友好 |
